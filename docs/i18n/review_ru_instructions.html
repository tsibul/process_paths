1# Measure Twice: input file format and rules for filling it in# Measure Twice: формат входного файла и правила заполнения
2This document is addressed to a language model that prepares a project file in a conversation with a person. The person does not read or edit the file: they load it into the application and see the result in its window. So the file must pass the check in full; the person will pass the check's remarks to you as they are.Документ адресован языковой модели, которая в разговоре с человеком готовит файл проекта. Человек файл не читает и не правит: он загружает его в приложение и видит результат в окне. Поэтому файл должен пройти проверку целиком; замечания проверки человек передаст тебе как есть.
3## 1. What the file describes## 1. Что описывает файл
4- **Entity** — something that has a state. **Axis** — one independent attribute of an entity. An axis has a list of **values**. - **Slice** — the values of all axes at one moment. - **Transition kind** — a change of the value of one axis of one entity: it was "from", it became "to". Nothing else changes in a transition. - **Transition** in a variant — a quadruple: transition kind, executor, instrument, scope. - **Variant** — a linear chain of transitions. There are no forks: a fork is written as two variants. - **Normalization** — the numbers. The **weight** of a transition = kind cost × scope coefficient × executor coefficient. The weight of a variant is the sum over its transitions. - **Check** — a flag of a transition kind. **Check axis** — the axis that such a kind changes. **Skip** — a check axis that stayed on its initial value; a skip has a price.- **Сущность** — то, у чего есть состояние. **Ось** — один независимый признак сущности. У оси — перечень **значений**. - **Срез** — значения всех осей в один момент. - **Вид перехода** — смена значения одной оси одной сущности: было «из», стало «в». Больше при переходе ничего не меняется. - **Переход** в варианте — четвёрка: вид перехода, исполнитель, инструмент, охват. - **Вариант** — линейная цепочка переходов. Развилок нет: развилка записывается двумя вариантами. - **Нормировка** — числа. **Вес** перехода = стоимость вида × коэффициент охвата × коэффициент исполнителя. Вес варианта — сумма по переходам. - **Проверка** — признак вида перехода. **Ось проверки** — ось, которую меняет такой вид. **Пропуск** — ось проверки, оставшаяся на начальном значении; у пропуска есть цена.
5The application knows nothing about the subject: all names are yours, in words, in the person's language. The numbers are assigned by the person; do not invent them silently — propose them and ask.Приложение ничего не знает о предмете: все названия — твои, словами, на языке человека. Числа назначает человек; не придумывай их молча — предложи и спроси.
6## 2. General rules## 2. Общие правила
7- One JSON file in UTF-8 encoding. - A reference is a name written letter for letter the same as in the place where it is declared (case, spaces, accents and other special characters). - Numbers are JSON numbers (`2`, `0.1`), not strings. - The order in lists matters: everything is shown in that order, and the first value of an axis is the initial one. - An optional field that is not needed is not written at all.- Один файл JSON в кодировке UTF-8. - Ссылка — это название, записанное буква в букву так же, как в месте, где оно объявлено (регистр, пробелы, «ё»). - Числа — числами JSON (`2`, `0.1`), не строками. - Порядок в списках значим: в этом порядке всё показывается, а первое значение оси — начальное. - Необязательное поле, которое не нужно, не пиши вовсе.

10### 3.1. Entities: `entities`### 3.1. Сущности: `entities`
11```json {"name": "Laundry", "axes": [ {"name": "state", "values": ["dirty", "washed", "put away"]} ]} ``````json {"name": "Бельё", "axes": [ {"name": "состояние", "values": ["грязное", "постирано", "убрано"]} ]} ```
12- Entity names are not repeated; axis names are not repeated within an entity; values are not repeated within an axis. - An axis has at least one value. **The first value is the initial one.** - An axis is one independent attribute. If two attributes change independently, they are two axes, not one axis with a list of combinations. - **Existence axis.** An entity that appears or disappears along the way gets an axis named as in `existence_axis.name`; among its values there must be `existence_axis.absent`. If this value is first, the entity does not exist at the start. While the entity does not exist, its other axes have no values. When it appears they get their initial values; when it disappears they lose them. - `inherit` (optional, on an axis): `[["Entity", "axis"], …]` — where the axis takes its value from at the moment the entity appears: from the first source that has a value and whose value is among the values of this axis; otherwise the first value of the axis.- Названия сущностей не повторяются; названия осей не повторяются внутри сущности; значения не повторяются внутри оси. - У оси есть хотя бы одно значение. **Первое значение — начальное.** - Ось — один независимый признак. Если два признака меняются независимо, это две оси, а не одна с перечнем сочетаний. - **Ось наличия.** Сущность, которая появляется или исчезает по ходу, получает ось с названием из `existence_axis.name`; среди её значений обязано быть `existence_axis.absent`. Если это значение первое, сущности в начале нет. Пока сущности нет, остальные её оси значений не имеют. При появлении они получают начальные значения, при исчезновении — теряют. - `inherit` (необязательно, у оси): `[["Сущность", "ось"], …]` — откуда ось берёт значение в момент появления сущности: от первого источника, у которого значение есть и оно входит в значения этой оси; иначе — первое значение оси.

16Rules:Правила:
17- A kind is a change of state, not an action of a particular person. Who does it and with what is written in the transition. Therefore **there cannot be two kinds with the same entity, axis, "from" and "to"**. - **A kind must not duplicate a chain of other kinds on the same axis.** If there are "a → b" and "b → c", a kind "a → c" cannot exist: one shift would be written in two ways. If a short path is needed, remove the intermediate value or write both steps. - The appearance of an entity is a kind on the existence axis from the "does not exist" value; the disappearance is a kind into that value. - It is convenient to make a check axis of two values: "not checked", "checked". The initial one is "not checked". - Check axes of different entities may have the same name: the price of a skip is written per pair "entity, axis". - A waiting kind (with `waiting`) has no labour: its cost in `kind_costs` is omitted or `0`, it cannot be `check: true`, and executor and scope coefficients do not apply to it. Waiting is summed per path separately from labour.- Вид — это смена состояния, а не действие определённого лица. Кто и чем делает, записывается в переходе. Поэтому **двух видов с одинаковыми сущностью, осью, «из» и «в» быть не может**. - **Вид не должен повторяться цепочкой других видов по той же оси.** Если есть «а → б» и «б → в», вида «а → в» быть не может: один сдвиг записывался бы двумя способами. Нужен короткий путь — убери промежуточное значение или запиши оба шага. - Появление сущности — вид по оси наличия из значения «не существует»; исчезновение — в это значение. - Ось проверки удобно делать из двух значений: «не проверено», «проверено». Начальное — «не проверено». - Оси проверки разных сущностей могут называться одинаково: цена пропуска записывается по паре «сущность, ось». - У вида-ожидания (с `waiting`) нет трудоёмкости: его стоимость в `kind_costs` не пишется или равна `0`, он не может быть `check: true`, коэффициенты исполнителя и объёма к нему не применяются. Ожидание суммируется по пути отдельно от трудоёмкости.
18### 3.3. Executors, instruments, scopes### 3.3. Исполнители, инструменты, охваты
19Three lists of names, without repeats within a list.Три списка названий, без повторов внутри списка.
20- Executor — who does it: a person, a program, a device. - Instrument — what it is done with. It is not part of the calculation, it only describes. - Scope — what the action falls on: on each unit or once for the whole batch. `batch_scope` names the "per batch" scope.- Исполнитель — кто делает: человек, программа, устройство. - Инструмент — чем делает. В расчёт не входит, только описывает. - Охват — на что приходится действие: на каждую единицу или один раз на всю пачку. `batch_scope` называет охват «на пачку».
21### 3.4. Variant parameters: `variant_params`### 3.4. Параметры варианта: `variant_params`
22A parameter is a named role that one of the executors fills in each variant. It is needed when a slice condition depends on who fills this role. If there is no such dependency, do not write the field.Параметр — названная роль, которую в каждом варианте занимает один из исполнителей. Нужен, когда условие среза зависит от того, кто эту роль занимает. Если такой зависимости нет, поле не пиши.
23```json "variant_params": ["recipient"] ``````json "variant_params": ["получатель"] ```
24Then **every** variant has: `"params": {"recipient": "Person"}`.Тогда у **каждого** варианта: `"params": {"получатель": "Человек"}`.
25### 3.5. Named slices: `named_slices`### 3.5. Именованные срезы: `named_slices`
26A named slice is a moment at which skips are counted. It is set by a condition; in a variant it is the first slice where the condition holds.Срез с именем — момент, на котором считаются пропуски. Задаётся условием; в варианте это первый срез, где условие выполнено.
27```json "named_slices": { "washed": {"any": [ {"states": [["Laundry", "state", "washed"]]} ]} } ``````json "named_slices": { "постирано": {"any": [ {"states": [["Бельё", "состояние", "постирано"]]} ]} } ```
28- `any` — a non-empty list of groups; one satisfied group is enough ("or"). - In a group all rows hold together ("and"). Rows are `states`: triples `[entity, axis, value]`, and `params`: pairs `[variant parameter, executor]`. A group without rows is not allowed. - The final slice always exists and is not written. The name `final` is taken. - If the condition did not occur in a variant, the slice coincides with the final one.- `any` — непустой список групп; достаточно одной выполненной группы («или»). - В группе все строки выполняются вместе («и»). Строки — `states`: тройки `[сущность, ось, значение]`, и `params`: пары `[параметр варианта, исполнитель]`. Группа без строк недопустима. - Конечный срез есть всегда, его не записывают. Название `final` занято. - Если условие в варианте не наступило, срез совпадает с конечным.

32The run of a variant is the main rule. A variant is executed step by step from the initial slice:Прогон варианта — главное правило. Вариант исполняется по шагам от начального среза:
331. Initial slice: for each entity of the variant each axis is on its first value (taking `initial` into account); for an absent entity only the existence axis has a value. 2. For each transition: the current value of the kind's axis must equal its `from`; all `requires` triples must hold. Then the axis gets `to`. 3. The first step where this is not so is an error of the variant.1. Начальный срез: у каждой сущности варианта каждая ось на первом значении (с учётом `initial`); у отсутствующей сущности значение есть только у оси наличия. 2. Для каждого перехода: текущее значение оси вида должно быть равно его `from`; все тройки `requires` должны быть выполнены. Тогда ось получает `to`. 3. Первый шаг, где это не так, — ошибка варианта.
34Before writing a variant, walk through it step by step yourself, keeping the slice in mind.Перед записью варианта пройди его по шагам сам, держа срез в уме.

38## 4. Work order## 4. Порядок работы
391. Find out from the person the process and the variants they want to compare; which of them are their own and which are someone else's; what task each variant solves. Do not go further without a task for each variant: ask the person for it. 2. Pick out entities and axes. Do not split too finely: an axis is needed if its value changes in at least one variant or stands in a condition. 3. Write the transition kinds; mark the checks. 4. Write the person's steps in their own words for each variant. Split each step into transitions and write `steps` next to `calls`. A step that gave no transition is not thrown away: write it with `calls: 0`. 5. Write the variants and run each one step by step. Set `task` for each variant — without it the file will not load. Variants with the same task are compared with each other; a variant with a unique task stays without a pair. 6. Agree the normalization numbers with the person. 7. Before handing over the file, show the person the chains as text: for each path its task, the steps in the person's words, and under each step its transitions; mark a step without a transition "no transition". Hand over the file only after the person agrees with the breakdown. 8. Check the file against the list in section 5.1. Выясни у человека процесс и варианты, которые он хочет сравнить; какие из них свои, какие чужие; какую задачу решает каждый вариант. Без задачи у каждого варианта дальше не иди: спроси её у человека. 2. Выдели сущности и оси. Мелко не дроби: ось нужна, если её значение меняется хотя бы в одном варианте или стоит в условии. 3. Запиши виды переходов; отметь проверки. 4. Запиши шаги человека его словами по каждому варианту. Разложи каждый шаг на переходы и запиши `steps` рядом с `calls`. Шаг, который не дал перехода, не выбрасывай: запиши его с `calls: 0`. 5. Запиши варианты и прогони каждый по шагам. Поставь `task` каждому варианту — без него файл не загрузится. Варианты с одинаковой задачей сравниваются друг с другом, вариант с единственной задачей остаётся без пары. 6. Согласуй с человеком числа нормировки. 7. Перед выдачей файла покажи человеку цепочки текстом: по каждому пути его задачу, шаги его словами, под каждым шагом его переходы; шаг без перехода пометь «нет перехода». Файл выдай только после того, как человек согласится с разбором. 8. Сверь файл со списком в разделе 5.
