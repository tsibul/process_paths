# procnorm: план устройства приложения

План, без кода. Приложение общего назначения: о предмете чужих моделей оно ничего не знает, все слова и числа приходят от пользователя. Пользователь файлов не читает и не правит: всё видит и вводит только в окне.

Слова плана: **справочник** — сущности, их оси и значения, виды переходов, исполнители, инструменты, охваты; **вариант** — линейная цепочка переходов; **срез** — значения всех осей в один момент; **нормировка** — числа: стоимость вида перехода, коэффициенты исполнителя и охвата, цена пропуска проверки; **вес** перехода — стоимость вида × коэффициент охвата × коэффициент исполнителя; **пропуск** — ось проверки, оставшаяся на начальном значении.

## 1. Как работает человек

### Версия 1. Загрузить и сравнить

1. Человек в разговоре с языковой моделью разбирает свой процесс: что меняется, какие есть варианты, какие числа.
2. Языковая модель по описанию формата готовит один файл проекта: справочник, варианты, нормировка.
3. Человек открывает приложение и загружает файл.
4. Если в файле ошибки, приложение показывает полный список замечаний. Человек копирует список языковой модели, получает исправленный файл и загружает его поверх.
5. Человек видит сравнительную таблицу: по каждому варианту — вес (всего и по исполнителям) и пропуски проверок с суммой цен. Таблицу можно сортировать, отбирать свои и чужие варианты, раскрыть вариант по шагам.
6. Справочник, варианты и нормировку можно посмотреть в окне, править нельзя.
7. Таблицу можно выгрузить в Markdown и CSV. Загруженные проекты остаются в списке.

### Версия 2. Графики

Рядом с таблицей — два графика, по линии на вариант, по горизонтали — номер шага. Человек видит, где по ходу пути варианты расходятся: где набирается труд и где делаются проверки.

### Версия 3. Править загруженное

Человек меняет в окне то, что загружено: числа нормировки, переходы в варианте, слова справочника; копирует вариант и меняет копию. Сравнение пересчитывается сразу. Ошибка правки показывается на месте, со строкой. Возвращаться к языковой модели ради одной цифры не нужно.

### Версия 4. Ручной ввод

Человек создаёт пустой проект и вводит всё в окне с нуля: справочник, варианты, нормировку. Языковая модель и файл не нужны.

## 2. Устройство

| Часть | Что делает |
|---|---|
| Ядро (есть, дорабатывается) | Проверяет проект, прогоняет варианты по шагам, считает вес и пропуски. Об окне и файлах не знает. Результаты не хранит |
| Файл проекта (новая) | Один файл JSON: справочник, варианты, нормировка. Загружается в базу целиком или не загружается вовсе; выгружается обратно |
| База (новая) | Все проекты пользователя в одном файле SQLite в папке данных. Ставить и настраивать нечего. Каждая правка записывается сразу |
| Окно (новая) | Список проектов и три вкладки: справочник; нормировка и варианты; сравнение. После переделок — четвёртая вкладка `Step chains`: пути как цепочки шагов человека с их переходами (`docs/decomposition_view_ru.md`). Сама не считает — все числа берёт у ядра. Подписи на английском |
| Выгрузка (частично есть) | Сравнение и подробности в Markdown и CSV |
| Командная строка (есть) | Те же проверка и расчёт без окна; нужна для сверки чисел с окном |
| Сборка (новая) | Готовая программа для Windows и Linux, запускается без Python |

Вид приложения — окно на компьютере пользователя (Python, PySide6). Причина: расчёт уже написан на Python; сети, сервера и учётных записей нет. Возражение: программу надо скачать, а неподписанная программа в Windows при первом запуске показывает предупреждение.

Что версия 2 рисует:

- **Цена по длине** — вес, накопленный после каждого шага. Вес каждого шага уже считается; не хватает только выдачи накопленной суммы по шагам.
- **Безопасность по длине** — сумма цен сделанных проверок на срезе после шага. Проверка сделана, если у оси проверки есть значение и оно не начальное; считаются все оси проверки справочника. Линия растёт, а опускается только там, где проверка откатилась на начальное значение. Вариант без проверок лежит на нуле. Проверки сейчас считаются только на именованных срезах и на конечном; не хватает счёта на каждом срезе.

Пути разной длины: по горизонтали номер шага, линия кончается на последнем шаге своего пути.

## 3. Порядок работ

Каждый кусок делается и проверяется отдельно.

### Версия 1

| № | Кусок | Как проверяется |
|---|---|---|
| 1 | Ядро: полный список замечаний вместо остановки на первом; замечания с местом | Тесты: на каждое правило — испорченный пример и ожидаемое замечание |
| 2 | Файл проекта: один файл с нормировкой, сторона варианта, номер формата | Расчёт по новому файлу равен расчёту нынешнего скрипта по тем же данным |
| 3 | База: запись и чтение проекта, загрузка из файла, выгрузка в файл | Файл → база → файл даёт тот же файл |
| 4 | Окно: список проектов (загрузить, загрузить поверх, выгрузить, скопировать, удалить); список замечаний с копированием; три вкладки только для просмотра; таблица сравнения с сортировкой, отбором по стороне, подробностями по шагам | Числа в окне равны выводу командной строки; проект после перезапуска на месте |
| 5 | Выгрузка сравнения в Markdown и CSV | Выгруженное равно показанному |
| 6 | Описание формата для языковой модели | Языковая модель по одному описанию готовит файл, который загружается без замечаний |
| 7 | Сборка для Windows и Linux | Запускается на чистом компьютере без Python |

### Версия 2

| № | Кусок | Как проверяется |
|---|---|---|
| 11 | Перенесён в переделку вкладки сравнения (coord-532): `series()` — накопленный вес, пропуски и сумма сделанных проверок после каждого шага; см. `docs/comparison_screen_plan_ru.md`, кусок 3 | Последняя точка равна итогу таблицы сравнения |
| 12 | Графики на вкладке сравнения; отбор вариантов тот же, что у таблицы. Два графика по линии на вариант (цена и безопасность по длине) и вид **шкала труда** (блок 3 макета `docs/mockups/comparison_steps.html`): полоса на вариант по общей оси труда, на полосе отметки проверок, пунктир — место именованного среза, цвет полосы — все проверки сделаны или есть пропуски | Точки графика и отметки шкалы равны числам `series()` |

### Версия 3

| № | Кусок | Как проверяется |
|---|---|---|
| 8 | Правка нормировки: ввод чисел, пересчёт сразу; при нехватке числа вариант получает «не задано», остальные считаются | Числа, введённые в окне, дают тот же расчёт, что те же числа в файле |
| 9 | Правка вариантов: добавить, убрать, переставить переход; копия и удаление варианта. Правка встраивается во вкладку `Step chains`, в место, оставленное справа от столбца `Scope` | Вариант после правки равен тому же варианту из файла; порча середины показывает нужную строку |
| 10 | Правка справочника; переименование не ломает варианты и нормировку; удаление используемого отклоняется со списком мест | После переименования расчёт не меняется |

### Версия 4

| № | Кусок | Как проверяется |
|---|---|---|
| 13 | Пустой проект; ввод справочника с нуля | Справочник из окна выгружается в тот же файл, что подготовленный заранее |
| 14 | Новый вариант с нуля; при добавлении перехода предлагаются только допустимые сейчас виды | Вариант из окна совпадает с тем же вариантом из файла |

## 4. Что не решено

Решено заказчиком:

- Четыре версии, как в разделе 1.
- Версии 2 и 3 переставлены: графики — версия 2, правка — версия 3; номера кусков прежние (заказчик).
- «Безопасность» числом — сумма цен проверок, сделанных к данному месту пути; линия растёт.
- **process-19.** Версия 1 отказывает в загрузке с замечанием, если в нормировке не хватает числа; «не задано» у варианта — с версии 3.
- **process-20.** На графике по горизонтали номер шага; линия кончается на последнем шаге своего пути.
- **process-21.** Проверка сделана, если у оси проверки есть значение и оно не начальное; считаются все оси проверки справочника; вернувшаяся на начальное значение перестаёт считаться. Линия безопасности растёт, а опускается только там, где проверка откатилась.
- **process-22.** Замечания — на английском, как окно; названия из справочника — как введены.
- **process-23.** Цена пропуска записывается по паре «сущность, ось»; одинаковые названия осей проверки у разных сущностей разрешены.
- **process-24.** Текста определений проекта и примечания к стоимости нет ни в файле, ни в окне.
- **process-25.** Если список сущностей варианта не задан, берутся сущности, которых касаются переходы варианта.
- Доработки после версии 1, до версии 2, каждая в своей ветке:
  1. переделка вкладки сравнения — `docs/comparison_screen_plan_ru.md`, ветка `comparison-groups`;
  2. показ декомпозиции — `docs/decomposition_view_ru.md`, ветка `decomposition-view`, после первой.
- **process-26.** Декомпозиция — отдельная вкладка `Step chains`. После загрузки окно остаётся на сравнении и предлагает перейти полосой со счётом путей и шагов без переходов. Модель показывает цепочки текстом в разговоре до файла. Команды `procnorm steps` нет.
- **process-27.** Срезы в цепочке — только меткой между шагами.
- **process-28.** Шаг без перехода показывается пустым, серым `No transitions`.
- **process-29.** Показ декомпозиции — после переделки сравнения.
- **ppm-11.** Вкладка `Step chains`: слева пути по тем же группам, что в сравнении; справа цепочка выбранного пути.
- Проекты хранятся в базе SQLite; файл — для загрузки, выгрузки и пересылки.

Решено без вопроса:

- Файл проекта — один, JSON; нормировка — его раздел. Названия полей — как в нынешнем скрипте, добавлены номер формата, название проекта и сторона варианта.
- Граница версий 3 и 4: версия 3 правит загруженное, версия 4 создаёт с пустого места.
- Сторон две; вариант без пометки — свой.
- Инструмент описывает переход, в расчёт не входит.
- Нормировка в проекте одна; другие числа — копия проекта.
- Срез, который в варианте не наступил, совпадает с конечным.
- Стоимость вида с признаком «вес 0» можно не писать; если написана — только 0.
- Файлы прежнего вида (модель и отдельная нормировка) приложение не принимает.

Решено при написании версии 1:

- Название приложения — procnorm. Папка и репозиторий не переименованы; прежний пакет `process_paths` остаётся, новый код — в пакете `procnorm` рядом и берёт из прежнего модель, прогон вариантов и проверку расщепления.
- Части: `procnorm/project.py` — чтение файла и замечания; `calc.py` — сравнение и шаги; `store.py` — база; `export.py` — выгрузка; `cli.py` — командная строка; `ui/` — окно. Тесты — `tests/test_procnorm_*.py`; первый файл тестов — пример из описания формата (`tests/data/laundry.json`).
- Замечания собираются по ступеням: строение файла; справочник, имена в вариантах и нормировка; прогон вариантов и проверка расщепления. Внутри ступени — полный список; следующая ступень идёт, только если предыдущая без замечаний, иначе одна ошибка даёт лавину ложных. По варианту — одно замечание, на первом не прошедшем шаге.
- Столбцы труда — исполнители с коэффициентом больше нуля, встречающиеся хотя бы в одном вызове; плюс столбец «всего» по всем вызовам. Одно правило вместо трёх.
- `batch_size` принимается, хранится и показывается; в расчёт не входит.
- `description` — описание проекта, `zero_weight_note` — пояснение к признаку «вес 0»; process-24 их не убирает: убраны только текст определений и примечание к стоимости.
- База версии 1: таблица проектов, файл проекта хранится целиком; номер схемы 1. Разложение по таблицам (раздел 2.3 устройства) — с правкой в версии 3, номер схемы 2.
- Выгрузка — на английском, как окно. Числа в таблице — с двумя знаками после запятой, в подробностях — без округления, как в устройстве.
- Вид — только светлая индиго-палитра макета; тёмной темы и смены палитры нет.
- Командная строка: `python -m procnorm` — окно; `check ФАЙЛ` — замечания; `table ФАЙЛ [--csv]` — сравнение.

Открыто, плану не мешает:

- Тёмная тема и руководство для человека — ни в одну из четырёх версий не входят.
- Не проверено: что сборка работает на Python 3.14 под Windows и сколько она весит.
