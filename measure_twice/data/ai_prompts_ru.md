# Measure Twice: шесть просьб для чата с ИИ

Человек говорит с чатом ИИ (ChatGPT, Gemini) в шесть шагов и только копирует просьбы ниже.
Каждый шаг — одна просьба; человек добавляет не больше одной-двух фраз, а на «Что проверить»
отвечает «да» или поправкой своими словами. Формат нужен только на шаге 5.
Шаг 6 строит программа, когда не принимает файл; он повторяется, пока файл не загрузится.

## Просьба 1. Задача

Первой, в новом чате. Вместо {task} — одна-две фразы о задаче.

```text
Мы подготовим файл для Measure Twice — программы, которая сравнивает пути выполнения одной задачи
по труду. Идём в шесть шагов; на каждый я дам просьбу. Правила на весь разговор:
- Каждый шаг делай сам. Не останавливайся, чтобы задать мне вопросы. Если не уверен, бери
  вероятный ответ.
- Каждый ответ заканчивай разделом «Что проверить»: 2-4 пронумерованных сомнительных места.
  Я отвечаю «да» или поправляю словами.
- Числа предлагай сам и помечай сомнительные.
- Все тексты и названия пиши на языке моей задачи.
- До шага 5 файл не пиши.

Шаг 1. Задача.
Моя задача: {task}

Дай задаче одно короткое название; оно общее для всех путей. Перечисли пути её выполнения, которые
ты понял из моих слов: короткое название, одна строка о том, что делается, и «свой» (мой) или
«чужой» (чей-то ещё). Затем добавь обычные пути, о которых я не сказал: только те, что правда решают
задачу, всегда «чужой». Название каждого добавленного пути заканчивай пометкой «(добавлен)» и
сохраняй её весь разговор и в файле; у названий действий пометки нет. Добавленный путь должен
отличаться от других действиями. В «Что проверить» назови каждый добавленный путь и спроси, каких
путей не хватает и какие лишние.
```

## Просьба 2. Шаги

Когда список путей согласован.

```text
Шаг 2. Шаги.
Распиши каждый согласованный путь по шагам. Шагов я не даю: напиши их сам, как работа делается
на самом деле.
- Включи обычные шаги: подготовку (перекрыть воду, отключить ток), проверку результата,
  уборку.
- Один шаг — одно действие, простыми словами. Скажи, кто его делает.
- Путь, где работу отдают кому-то (наёмному работнику, службе), перечисляет шаги этого работника.
- Если два пути приходят к одному результату по-разному, скажи, над какой частью работает каждый
  шаг (заменить прокладку, подтянуть гайку, обмотать резьбу), а не просто «починить».
- У пути без проверки нет шага для неё, даже «проверка не делается».
- Отметь каждый шаг, где человек только ждёт (сантехника, доставку), и дай примерную
  длительность.
- В «Что проверить» одним пунктом назови шаги, которые ты добавил и которых нет в моих словах.
Покажи пронумерованный список для каждого пути. Формата файла пока нет.
В конце — «Что проверить»: 2-4 шага, в которых ты меньше всего уверен.
```

## Просьба 3. Одинаковые действия и проверки

Когда шаги согласованы.

```text
Шаг 3. Одинаковые действия и проверки.
Пройди по шагам всех путей вместе.
1. Одно и то же действие называется одинаково во всех путях, слово в слово.
2. Для каждого действия скажи, что оно меняет: один признак одной вещи, из одного состояния
   в другое. Пример: «Заменить прокладку: Прокладка, изношена -> новая».
3. Два действия никогда не делают одну и ту же смену. Разные способы прийти к одному результату
   действуют на разные части: Прокладка, изношена -> новая; Гайка, ослаблена -> затянута.
4. Действию без своей смены дай новый признак (Пол: мокрый -> сухой). Никогда не вешай его
   на смену другой вещи. «Без труда» — только работа, где труда нет.
5. Отметь проверки: проверка подтверждает результат после действия, и у её пропуска есть цена.
   Если в моих словах действие названо проверкой, это проверка. Иначе поиск причины поломки —
   обычное действие. Проверка меняет свой признак, а не то состояние, на которое смотрит:
   «Проверить на течь: Кран, течь не проверена -> проверена», «Осмотреть уплотнение: Прокладка,
   не осмотрена -> осмотрена». У пути без проверки нет шага для неё; признак проверки у вещи
   всё равно есть, поэтому пропуск виден.
6. Скажи, что появляется или исчезает по ходу (подставленное ведро, записанный визит).
   Часть, которая уходит вместе с другой вещью, получает своё действие без труда:
   сделай ту же вещь отсутствующей признаком наличия (Прокладка: наличие да -> нет, выброшена со
   старым краном); никогда не заводи новую вещь для старой части. Тогда её проверки не пропущены.
7. Ожидание кого-то — отдельный вид действия: не проверка и не труд. Оно тоже меняет свой
   признак (Визит сантехника: записан -> состоялся).
Затем прогони каждый путь: каждое действие начинается из состояния, которое оставило предыдущее.
Исправь те, что не сходятся.
Покажи таблицу: действие | вещь | признак | из -> в | проверка. Затем каждый путь как названия
действий.
В конце — «Что проверить».
```

## Просьба 4. Кто и сколько

Когда действия и проверки согласованы.

```text
Шаг 4. Кто и сколько.
1. Перечисли исполнителей: кто или что делает действия.
2. Дай каждому коэффициент: какая доля его труда засчитывается, 1 — для главного человека.
   Коэффициент 0 — только для машины или программы, которая работает сама. Никогда не 0 для
   человека, наёмного тоже. Каждый коэффициент 0 вынеси в «Что проверить».
3. Дай каждому действию стоимость труда в одной единице на весь проект (минуты или баллы).
   Оплата — не труд: действия для неё нет. Ожидание кого-то — действие с длительностью
   в часах или днях, а не со стоимостью или весом: пометь каждое знаком «?». Короткое ожидание,
   длительность которого не нужна (стекает вода), стоит 0.
4. Скажи, делается ли каждое действие один раз на всю работу или на каждую единицу; если на
   единицу — сколько единиц в пачке.
5. Для каждой проверки дай цену её пропуска, больше 0, в единице труда, сравнимую с работой
   по исправлению того, что пропуск пропустит. Никогда не прибавляй её к труду.
6. Покажи итог каждого пути: сумма стоимость x коэффициент исполнителя x коэффициент охвата.
   Если шаги не из моих слов заметно меняют итог пути, скажи об этом в «Что проверить».
Сомнительные числа пометь знаком «?».
В конце — «Что проверить».
```

## Просьба 5. Файл

Когда исполнители и числа согласованы.

```text
Шаг 5. Файл.

Только действия, согласованные на шагах 2-4; без подготовки (достать или убрать инструмент),
которой я не называл. Сначала сам прогони каждый путь по осям. Затем «Что проверить»: твои выборы.

ФОРМАТ
Ссылка — объявленное название буква в букву. Числа — числами JSON. Порядок важен.
В списке названия не повторяются. Ненужных необязательных полей не пиши.

Верхний уровень (* обязательно): format* = 1; name*; existence_axis* {"name","absent"};
entities*; kinds*; executors*, instruments*, scopes* - списки названий; batch_scope* - охват
«один раз на пачку»; named_slices; variants*; normalization*.

entities: {"name", "axes": [{"name", "values": [...]}]}. ПЕРВОЕ значение - начальное.
Ось - один независимый признак. Появляющаяся или исчезающая вещь получает ось
existence_axis.name с первым значением existence_axis.absent; пока вещи нет, другие её оси
без значения. Обычная ось так не называется.

kinds: {"name", "entity", "axis", "from", "to"} и необязательные:
requires [[сущность, ось, значение], ...] - что должно быть до; не своя сущность и ось
вида: это уже в "from";
check: true - подтверждает результат; на оси проверяемой вещи;
zero_weight: true с zero_weight_note - шаг без труда (стекание).
waiting: число > 0 с waiting_unit "hours"|"days" - ожидание кого-то: без стоимости, не проверка.
from != to. Нет двух видов с одинаковыми entity, axis, from и to. Нет вида в обход цепочки
(a->b, b->c, значит нет a->c). Действию без своей оси - новая ось.

named_slices (необязательно): {"имя": {"any": [{"states": [[сущность, ось, значение], ...]}]}} -
пропуски считаются, когда впервые выполнится одна группа. "final" занято.

variants: {"code" (мои, если я их дал), "title", "side": "own" (свой)|"other" (чужой), "task",
"calls", "steps"}. Сравниваются пути с одинаковым task. calls - [вид, исполнитель,
инструмент, охват]; каждый начинает со значения, оставленного предыдущим; все requires
выполнены. У пути без проверки нет вызова для неё.
steps - [{"text": шаг моими словами, "calls": сколько вызовов подряд}]; calls может быть 0;
сумма равна числу вызовов.

normalization: kind_costs {вид: стоимость} для каждого (zero_weight, waiting: 0 или нет);
executor_coefficients {исполнитель: k} для каждого, 0 только для машины или программы;
scope_coefficients {охват: k} для каждого (на единицу 1, на пачку 1/размер пачки);
axis_skip_prices {сущность: {ось проверки: цена > 0}} для каждой оси проверки и только для них,
к труду не прибавляется; batch_size необязательно; labour_per_waiting_hour не пиши: его задаю я.
Без отрицательных чисел и лишних названий.

ПРИМЕР
```

## Просьба 6. Замечания

Эту просьбу строит программа, когда не принимает файл; человек её только вставляет.

```text
Шаг 6. Замечания.
Программа не приняла файл. Её замечания:
{remarks}

Исправь каждое замечание. Затем снова проверь весь файл по формату шага 5, а не только названные
места: замечания могут приходить частями. Снова прогони каждый путь по осям: каждый вызов
начинается со значения, которое оставил предыдущий. Сохрани всё, о чём мы договорились; меняй
только то, что нужно для исправления, и одной строкой на замечание скажи, что изменил.
Дай весь файл снова в одном блоке кода, а не его часть.
В конце — «Что проверить», только если исправление изменило что-то согласованное.
```
